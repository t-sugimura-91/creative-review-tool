# 制作物チェックツール 要件定義（ドラフト v0.1）

作成: 2026-11-08 開発部（lp-development）／ CMO監査前のドラフト。社長の決定が必要な点は末尾に集約。
置き場: このフォルダには要件・規約だけを置く。コードは別リポジトリ（案 `creative-review-tool`、プライベート）。

## 1. 目的
自社（SET UP）とクライアントが、制作物を同じ画面で確認し、コメントと承認状態を残せるようにする。

## 2. 前提（社長の指示と調査による）
- クライアントは当面10社。メールアドレスで登録してログインする（社長指示 2026-11-08）
- 制作物の種類: 画像、動画、文章、LP（社長了承）
- コーポサイト `setup-inc.com` は GitHub Pages の静的HTML（2026-11-08 公開ページとヘッダーで確認。中身のリポジトリは未確認）。サーバー処理を持てないため、ツールは別サブドメイン（案 `review.setup-inc.com`）の別ホスティングに置く
- 事実と推測: 上記の構成案（Supabase等）は推測で、未検証

## 3. 利用者と権限
| 役割 | できること |
|---|---|
| 管理者（SET UP） | 全社の案件・制作物の閲覧、アップロード、版の管理、ステータス変更、クライアントの招待・停止 |
| クライアント | 自社の案件の制作物だけ閲覧、コメント、「確認OK」「修正依頼」の入力 |

- 他社の制作物・コメント・メンバーは、一覧にもURL直打ちにも出さない（行単位のアクセス制御をDB側で強制する）
- クライアントの招待は管理者のみ。自己登録は招待メールのアドレスだけ許可する
- 1社に複数ユーザーを紐づけ可能（想定は1社あたり数名）

## 4. 認証
- メールのリンク認証（パスワードを持たない）を第一案。ワンタイムリンクの有効期限は短く設定する
- セッション期限、ログアウト、招待の取り消しを用意する
- 認証情報・APIキーはコードとこのリポジトリに書かない（環境変数／シークレット管理）

## 5. 機能（MVP）
1. 案件（クライアント単位の中に案件）の作成・一覧
2. 制作物のアップロードと版管理（案件ID、制作物ID、版数、メモ）
3. 種類別の表示
   - 画像: 拡大表示、PC／スマホ幅の見え方、広告枠サイズの表示
   - 動画: 再生、コメントの時刻指定
   - 文章: 本文表示、差分（前の版との比較）
   - LP: 公開前URLの埋め込み表示、または画面キャプチャ（検証環境のURLは認証付き）
4. コメント（全体コメントと、画像・動画上の位置／時刻指定コメント）
5. ステータス: 下書き → クライアント確認中 → 修正依頼 → 確認OK
6. 通知: 確認依頼・修正依頼・確認OKをメールで通知（本文に制作物の内容は載せず、ログイン先リンクだけ）
7. 操作履歴（誰が、いつ、何をしたか）

## 6. 審査・承認との関係（ルールとの整合）
- ツール上の「確認OK」は、クライアントの確認であり、審査部の「審査通過」と社長の承認の代わりにならない
- 審査部の「審査通過」を、ツール上に別の項目として表示するかは社長の決定（末尾）
- クライアントへ制作物を見せる操作（アップ、確認依頼の送信）は、外部への送信にあたる。人間の承認が必要な操作として扱い、事前承認ルール（`clients/<社名>/operations-rules.md`）で範囲を決められる
- 他社案件の流用禁止（`clients/<社名>/`の方針）を、ツールの権限設計で担保する

## 7. このリポジトリからのアップ
- 流れは一方向: このリポジトリで作成 → 審査部の審査 → 承認 → ツールのアップロードAPIへ送る
- アップ用の認証トークンは環境変数に置く。チャットやファイルには書かない
- 案件ID・版数は、アップの都度、こちらで採番して付ける
- アップの自動化は `automation-build` で別途設計する（MVP後）

## 8. 非機能要件
- スマートフォンで確認できる（クライアントは外出先で見る想定）
- 個人情報は最小限（メールアドレスと表示名のみ）。制作物に顧客の個人情報を含めない運用とする
- 動画・画像は暗号化して保存し、署名付きの期限付きURLで配信する
- `noindex`を全ページに設定し、検索エンジンに載せない
- バックアップと、削除時の復元期間を設ける。データの削除は社長の承認を要する操作として扱う
- 計測: ツールの利用状況はGA4等のタグを入れず、必要最小限の操作履歴だけを持つ

## 9. 構成案（推測。要件確定後に比較して決める）
- 公開先: `review.setup-inc.com`（DNSにサブドメインのレコードを追加するだけ。コーポサイト本体のファイルは触らない）
- 認証・DB・ファイル保存を1つで賄えるマネージドサービス（例 Supabase）＋ 静的フロントのホスティング
- 比較する観点: 日本リージョン、料金（10社規模）、行単位アクセス制御、動画保存容量

## 10. 計測イベント
- login、view_asset、comment_add、status_change、upload_version（すべて操作履歴として自社DBに保存。広告媒体のタグは設置しない）

## 11. テスト項目（実装時）
- クライアントAのユーザーで、クライアントBの案件URLを直打ちして拒否される
- 招待されていないメールアドレスで登録できない
- 取り消した招待、期限切れリンクで入れない
- スマホ幅での表示、動画再生、画像拡大
- 通知メールにファイルや内容が載らない

## 12. 公開手順・切り戻し（概要）
1. 検証環境で上のテストを通す
2. 審査（セキュリティ観点）→ CMO監査 → 社長承認
3. DNS追加とドメイン設定（社長承認後）
4. クライアントを1社ずつ招待（招待メールの送信も承認後）
- 切り戻し: 招待を止める、DNSのレコードを外す。データは削除しない

## 13. 残る課題・社長の決定が必要な点
1. ホスティング先とリポジトリ新規作成（名前案 `creative-review-tool`、プライベート）
2. コーポサイトのリポジトリの場所と所有アカウント（コラム側の設計に必要）
3. ツール上に「審査通過」を表示するか
4. クライアントへの確認依頼の送信を、個別承認にするか、事前承認ルールにするか
5. DNS（`review.setup-inc.com`）の追加の承認と、ドメイン管理者の確認
6. 利用規約・プライバシーの扱い（クライアントに制作物を預かる旨。審査部で確認）
